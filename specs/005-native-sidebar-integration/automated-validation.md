# Automated Validation and Delivery Boundaries

**Feature**: [Native Sidebar Integration](spec.md) · **Date**: 2026-10-24

This defines required future evidence, not passing tests. All cases currently have status **not run — feature not implemented**. No human approval, manual walkthrough, usability study or screenshot inspection is required to validate runtime behavior. User approval of the specification is a separate planning authorization.

## Mandatory Automation Adaptation

1. Reuse current Node/Angular tests, real `@vscode/test-electron` host integration, fixture corpus and downloaded Desktop/installed-VSIX provisioning. Add assertions at existing owners instead of duplicating XML engines or replacing native tests with mocks.
2. Introduce the smallest justified **test-only TypeScript Desktop UI driver**, initially evaluating pinned Playwright Electron support against the actual VS Code executable. Its bootstrap must launch a clean profile, open the installed extension, activate a native view, navigate a row, reach the real Angular webview and capture the actual workbench. Test launch/fuse/webview limitations on target platforms before selecting the final pinned dependency. Document license/necessity, keep it out of the VSIX and add no production server.
3. If this candidate driver cannot automate a required interaction, investigate an appropriate maintained Desktop driver or adapt the test harness. Record failing operation, binary/driver versions, attempted method and missing observable proof. A stubbed interaction, compile, synthetic Angular-only page or human confirmation cannot close the criterion. Keep mandatory coverage blocked until a reliable automated path exists.
4. Add root `test:e2e` and `test:visual` commands (proposed, not currently implemented). Integrate them into GitHub Actions required checks and applicable tag quality gates. Run native/package/functional Desktop compatibility on the existing minimum/stable OS matrix; reference screenshot comparisons use a separate fixed environment. Build before compiled suites as required by current scripts. Retain format, lint, typecheck, unit, roundtrip, compatibility, acceptance, release, build, package, native and package checks.
5. Never treat a suite with skipped required cases, an unavailable driver, missing baselines or absent artifacts as passing acceptance. Assertions and their independent expected results must exist before claiming implementation slices complete.

## Deterministic Visual and Timing Environment

- Pin the reference VS Code version/build, test driver, OS/runner image, display/fonts and dependencies. The current minimum `1.142.0` is the initial reference candidate; its installed build must pass bootstrap. A moving `stable` channel remains a functional compatibility target, not a shared screenshot reference.
- Use a clean disposable profile, local deterministic fixtures, fixed sidebar/panel widths, English locale, fixed timezone, disabled update/extension-recommendation/telemetry noise and unrelated extensions. Do not modify the user's real profile.
- Reference Desktop window/display: 1440 × 1000 pixels, DPR 1, host zoom level 0 (100%). Record actual workbench/editor content bounds; exercise separate 200% interface-scaling cases and record effective bounds. Cover inherited designer areas 1280 × 800, 1024 × 768, 640 × 480 and 400 × 600 through controlled layout/window configurations, not invented equivalence with full window dimensions.
- Reference themes: bundled Light+, Dark+, High Contrast and High Contrast Light. Record theme IDs/builds; use actual host themes, not a browser-only preferred-color-scheme substitute. Verify supplied activity SVG through the host's rendered icon path.
- Wait for deterministic ready/accepted-version/rendered-state conditions and loaded fonts. Disable nonessential animations and caret blink for references; freeze unrelated volatile content only. Never mask selection, focus, icon, clipping, menus or canvas boundaries being tested.
- Commit reference PNGs and their metadata when the UI exists. Tests fail on absent references and compare expected/actual/diff with pinned thresholds: exact dimensions; per-pixel color tolerance at most 0.1 and mismatching-pixel ratio at most 0.001 on unmasked reference regions. Semantic/geometry/contrast assertions remain mandatory even below that threshold. If reproducibility requires different thresholds, record measured repeatability and amend the test contract before relaxing them; do not accept arbitrary drift.
- No automatic baseline update in CI. Initial/update baselines are generated reproducibly and checked against explicit layout/state/contrast oracles; human image approval is not a mandatory gate. Missing baselines keep affected criteria unvalidated.
- Assert ≥4.5:1 normal-text and ≥3:1 essential-boundary/focus/selection contrast from actual rendered reference colors, accounting for compositing. Check visible focus under keyboard input; a DOM class alone does not prove visibility.
- For timing, collect real input-to-observed rendered-state samples with actual displayed-state evidence and independent accepted XML where applicable. Record sample arrays and percentile/count calculation. `requestAnimationFrame`, host completion, synthetic timers or mocked snapshots alone do not establish a visible result. Use bounded screenshot/presented-frame observation; document sampling resolution and include it in the measured bound. For layout stability, record continuous frame/bounding-box samples while input is held, not just before/after screenshots.

## Evidence and Completion Rules

Record each requirement/scenario/edge/SC with test identifier, fixture IDs, expected oracle, candidate commit and VSIX digest, platform, Desktop build, driver/dependency versions, locale/fonts/theme, viewport/DPR/scaling/report zoom, executed outcome and artifact links. Save raw timing samples, selection/race assertions, network-attempt logs and expected/actual/diff images or traces on failure using minimum-permission GitHub Actions artifacts. Use per-platform failure logs without secrets or image/query payloads.

Any absent or failed mandatory assertion means **not validated** and blocks the feature's completion. The only conditional scope is native-to-webview drag: a proven limitation yields an explicitly unavailable capability with passing activation/fallback assertions, not a claim that native drag passed. Functional acceptance cannot be inferred from specification review, task checkboxes, successful compilation or historical manual evidence.

## Platform Scope and Disabled Cases (CI run 40418317992)

These cases are explicitly scoped or skipped. A skipped case is **UNVALIDATED** on that platform: it is never reported as passed, and the run records it in `runner-status.json` (`unvalidatedHostObserver` for the host-observer cases, `unvalidatedPlatformSkips` for the other platform-scoped skips). Both the test-side skip and the runner allowlist come from `tests/desktop/host-observer-scope.ts`; a skip not listed there for that platform fails the run, and Linux accepts none. Everything not listed here keeps running and stays mandatory on every platform.

### Mandatory native host observation is Linux-only

The host observer (strace process-tree capture plus iptables owner-uid blocking) exists on Linux only. Windows (ETW/WFP) needs elevation that CI runners do not grant, and macOS has no unprivileged observer. On `win32` and `darwin` the following Playwright cases call `test.skip` with that reason (`tests/desktop/host-observer-scope.ts` owns the list):

| Case | Why it depends on host observation |
| --- | --- |
| `security-observer.spec.ts` "security observer: real trust states, host tree and webview attempts fail closed" | Native host capture and blocking control (also the capability probe) |
| `offline.spec.ts` `FR-030-trust` | Provisions its own blocked session |
| `offline.spec.ts` `SC-009-monitored-offline`, `FR-014-no-fetch`, `EDGE-05-inert` | Each provisions its own blocked session through FR-030's setup |
| `offline.spec.ts` `US6.4-trusted-restricted` | Repeats the monitored journeys under real restricted and trusted profiles |

On Linux they remain mandatory: an unsupported or incomplete capture is a failure. `tests/desktop/run-tests.ts` accepts these skips only off Linux and only for these titles; any other skip still invalidates the run. In `--probe` mode the `securityObserver` capability is recorded as `unsupported` (never `passed`) off Linux and only that capability may be unsupported. AT-09 (offline, trust, host-observed network attempts) is therefore not validated on Windows or macOS.

### Metadata-only host observer allowances

The Linux host observer (`tests/desktop/security-observer.ts`) classifies every file syscall of the VS Code process tree against an allowlist. Besides the writable and read-only roots, a few benign host probes are allowed by metadata calls only (the last row below is the one exception: fixed system paths that the VS Code binary may also open read-only); opening, reading, writing, watching or executing the same paths stays unexpected, and the credential denylist is applied first.

| Probe | Allowed |
| --- | --- |
| Executable-based extension tips (shared process `ExtensionTipsService` looking for `docker`, `mvn`, `gradle`, `subl`, `eclipse`...) | `stat`, `lstat`, `newfstatat`, `statx`, `access`, `faccessat`, `faccessat2` on a path whose parent directory is exactly one of the absolute entries of the `PATH` the observed VS Code was launched with (`AllowedAccess.path`). Empty and relative entries are ignored, and files in subdirectories of an entry do not match. Entries that could stand for user data are also dropped: `/`, the home directory, the OS temporary directory, and any entry equal to, an ancestor of, or inside an allowed root (profile, workspace, fixtures, extensions). `extensions.ignoreRecommendations` does not stop these probes. |
| Executable-based extension tips probing the home directory (the same service also looks for `<userHome>/<exe>`, besides `/usr/local/bin/<exe>` and `/usr/bin/<exe>`) | `stat`, `lstat`, `newfstatat`, `statx`, `access`, `faccessat`, `faccessat2` on a path whose parent directory is exactly the home directory and whose basename is one of a fixed list of executable names (`EXE_TIP_NAMES`: `docker`, `mvn`, `gradle`, `git`, `subl`, `kubectl`...). The list is the set of `exeBasedExtensionTips` keys of the bundled VS Code 1.143.1 `product.json` that are valid Linux file names (the Windows-only entries with spaces are left out). Opening, reading, executing or writing the same paths, dotfiles (`~/.docker`), other names and subdirectories (`~/sub/docker`) stay unexpected. This rule is independent of `PATH`, which never covers the home directory. |
| VS Code Electron binary start-up probes (libselinux and GnuTLS initialisation, Ubuntu kernel signature; seen as intermittent `US6.4` restricted-window reports on Linux, VS Code 1.142 and 1.144) | Exactly these paths and no others: `/sys/fs/selinux` and `/selinux` (`statfs`), `/etc/selinux/config` (`access`), `/etc/gnutls/config` (`newfstatat`, `openat`) and `/proc/version_signature` (`openat`). Read-only: the stat-family calls (`stat`, `lstat`, `newfstatat`, `statx`, `access`, `faccessat`, `faccessat2`, `statfs`) and `open`, `openat`, `openat2` without a write flag (`O_WRONLY`, `O_RDWR`, `O_CREAT`, `O_TRUNC`, `O_APPEND`). Only when the trace attributes the call to exactly the VS Code Electron binary of the test install (`AllowedAccess.hostExecutable`, by default `<exec root>/code`, compared on the raw executable path before sanitization); a different executable, an unknown executable (never exec'd in the trace, or already exited) or a look-alike path is unexpected. No prefixes or trees: other files below `/etc/selinux` or `/etc/gnutls`, a child of an allowed path and `readlink` stay unexpected, and the credential denylist is applied first. Justification: these are operating-system configuration reads the Electron binary performs by itself on every start; they hold no user data and open no network connection. |
